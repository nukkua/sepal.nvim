*sepal.txt*  Delegate, verify, land: specs for Claude Code

==============================================================================
1. INTRODUCTION                                                        *sepal*

You write a spec next to your code; Claude Code works on it in a git worktree
(your files never change under you); sepal runs the spec's check itself; if
it passes, the result lands in your work tree as unstaged changes, to review
with the git tools you already use. You hear about it when it's landed or
when something needs you. |:Sepal-inbox| lists every spec.

Requirements: Neovim 0.12+, Claude Code, git. Optional: fff.nvim to pick
files, fidget.nvim for a spinner.

==============================================================================
2. TUTORIAL                                                   *sepal-tutorial*

1. Map two keys:
>lua
   vim.keymap.set({ "n", "x" }, "<leader>as", ":Sepal spec<cr>")
   vim.keymap.set("n", "<leader>ai", "<cmd>Sepal inbox<cr>")
<
2. Select the code you mean (or don't) and press <leader>as. Fill in the
   spec. "Done when:" is a shell command that has to pass, e.g. `make test`.
3. <c-c><c-c> sends it. Keep working; more specs run in parallel.
4. "✓ landed: …" means it passed the check and is in your files, unstaged.
   The "·" lines under it are the decisions the agent made alone: read them.
5. Review with `git diff`, gitsigns, fugitive. |:Sepal-undo| takes it back.
6. A warning means it needs you: <leader>ai shows why; `r` replies to the
   agent, `L` lands anyway, `o` opens its chat.

==============================================================================
3. SETUP                                                         *sepal-setup*

`setup()` is optional. These are the defaults:
>lua
  require("sepal").setup({
    cmd = { "claude" },
    args = { "--permission-mode", "acceptEdits" },
    check = nil,
    retries = 1,
    land = "auto",
    prepare = nil,
    worktrees = vim.fn.stdpath("state") .. "/sepal",
    spec_suggest = nil,
    open = nil,
  })
<
`cmd`        the agent. A spec runs `cmd -p --output-format stream-json
             --verbose <args>` in its worktree, with the spec on stdin.
                                                                *sepal-args*
`args`       added to each run. The spec's check is always allowed. Nobody
             answers permission prompts, so other tool calls that need one
             are refused and sepal names them ("the agent was not allowed:
             Bash(npm run lint)"). Allow what you trust:
             `{ "--permission-mode", "acceptEdits", "--allowedTools",
             "Bash(npm run lint)" }`. Other flags too: `"--model", "opus"`.
`check`      the check for specs without a "Done when:" line, e.g.
             "make test". nil: those specs aren't checked.
`retries`    when the check fails, the agent gets its output and this many
             more tries.
`land`       "auto": a spec that passes lands by itself, when it lands
             cleanly. "manual": it waits in the inbox for `L`.
`prepare`    shell command run in each new worktree before the agent, to
             bring in what git doesn't have: `ln -s "$SEPAL_ROOT/node_modules"
             node_modules`. $SEPAL_ROOT is your repo. What it makes isn't
             counted as the agent's work.
`worktrees`  where the worktrees and each repo's inbox (JSON) live.
`open`       function(argv, cwd) that shows a spec's chat. Default: a new
             tmux window; outside tmux the command is copied.
                                                       *sepal-spec_suggest*
`spec_suggest` argv that gets the spec buffer on stdin (your idea and
             Files:) and prints the finished spec. <c-c><c-s> runs it. For
             Claude Code, pass -p and --no-session-persistence.

==============================================================================
4. COMMANDS                                                    *sepal-commands*

                                                                      *:Sepal*
:[range]Sepal [spec]
                  Write a spec in a buffer above the code: Scope, Goal,
                  Constraints, Done when, Files. In it:
                    <c-c><c-c>  send it and close the buffer
                    <c-c><c-s>  have |sepal-spec_suggest| write the spec
                    <c-c><c-f>  add a file under Files: as @path
                    <c-c><c-k>  discard the spec
                  With a [range], those lines go in as a "Selection:
                  path:10-20" code block. Closing the window keeps the
                  draft. Outside a git repo the spec stays in its buffer.
                                                               *:Sepal-inbox*
:Sepal inbox      Every spec of this repo, newest first, with what to read
                  under each (assumptions, why it needs you, the failing
                  check's output). In it:
                    <CR>  everything the spec changed, as a diff (q closes)
                    L     land it (with conflict markers if it overlaps
                          your edits)
                    u     take a landed spec back out
                    r     reply: the agent continues in the same chat from
                          what it did; it's checked and lands again (only
                          what's new)
                    o     open its chat (see `open`)
                    x     stop it
                    D     drop it
                    q     close the inbox
:Sepal land       Land the newest spec that's waiting.
                                                                *:Sepal-undo*
:Sepal undo       Take the newest landed spec back out (a merge too: your
                  edits since stay).
:Sepal open       The newest spec's chat in Claude Code (`claude --resume`).
:Sepal stop       Stop every running spec.
:Sepal clean      Drop the specs that are over: landed, no changes, undone,
                  stopped, interrupted.

Lua: `require("sepal").spec()`, `.inbox()`, `.land()`, `.undo()`, `.open()`,
`.stop()`, `.clean()`.

==============================================================================
5. HOW IT WORKS                                                 *sepal-landing*

Your work tree (uncommitted and untracked files too) is saved as a commit
through a temporary index; your index and branches aren't touched. The agent
works in a worktree of it, then sepal runs the check there. Landing applies
the change to your work tree with a three-way merge per file (git
merge-file), unstaged. With land = "auto" it only lands when that's clean: no
overlap with your edits and no unsaved buffer of a file it touches; otherwise
the spec waits as "needs you". Results are kept as refs/sepal/<id>/* until
the spec is dropped. A spec running when Neovim quits shows as "interrupted";
`r` continues it.

6. HEALTH                                                       *sepal-health*

`prepare`, `open`, `spec_suggest`, fidget and fff.
